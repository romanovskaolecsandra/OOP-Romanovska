# Звіт до самостійної роботи №14
**Тема:** Кейси Polly/Retry: короткий звіт

---

## 1. Досліджені сценарії відмовостійкості

### Сценарій 1: Тимчасові збої підключення до бази даних (`DatabaseRetryScenario`)
* **Опис проблеми:** Під час пікового навантаження або короткочасного розриву мережі запит до бази даних може завершитися помилкою очікування з'єднання (`TimeoutException`) або взаємоблокуванням (*deadlock*). У більшості випадків повторний запит через частку секунди проходить успішно.
* **Обрана політика та обґрунтування:** `Retry` із параметрами `BackoffType = DelayBackoffType.Exponential` та `UseJitter = true`.
  * Експоненційна затримка (400 мс → 800 мс → 1600 мс) дає базі даних час відновитися.
  * `Jitter` (випадкове відхилення часу) запобігає ефекту «громового стада» (*Thundering Herd*), коли сотні клієнтів одночасно повторюють запит в одну й ту саму мілісекунду.
* **Фрагмент коду налаштування пайплайну:**
```csharp
var pipeline = new ResiliencePipelineBuilder<string>()
    .AddRetry(new RetryStrategyOptions<string>
    {
        ShouldHandle = new PredicateBuilder<string>().Handle<TimeoutException>(),
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromMilliseconds(400),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true
    })
    .Build();
```
* **Очікувана поведінка та лог:** Перші дві спроби завершуються винятком `TimeoutException`, стратегія логує кожен `[Retry]` із розрахованою затримкою, а третя спроба успішно повертає дані замовлення.

### Сценарій 2: Тривала відмова платіжного шлюзу (`PaymentCircuitBreakerScenario`)
* **Опис проблеми:** Якщо зовнішній платіжний мікросервіс повністю впав (HTTP 503), звичайний `Retry` лише погіршить ситуацію: кожен користувач чекатиме на кілька невдалих спроб, вичерпуючи потоки вебсервера та створюючи лавиноподібне навантаження на хворий сервіс.
* **Обрана політика та обґрунтування:** Комбінація **`Circuit Breaker`** (розмикач ланцюга) + **`Fallback`** (резервна дія).
  * Після 3 невдалих запитів `Circuit Breaker` переходить у стан **Open** на 2 секунди і миттєво відхиляє нові запити винятком `BrokenCircuitException` без звернення до мережі.
  * Зовнішній `Fallback` перехоплює помилку і повертає користувачеві коректне повідомлення про постановку платежу в чергу замість падіння програми. Через 2 секунди у стані **Half-Open** пропускається пробний запит, який після успіху повертає ланцюг у стан **Closed**.
* **Фрагмент коду налаштування пайплайну:**
```csharp
var pipeline = new ResiliencePipelineBuilder<string>()
    .AddFallback(new FallbackStrategyOptions<string>
    {
        ShouldHandle = new PredicateBuilder<string>()
            .Handle<InvalidOperationException>()
            .Handle<BrokenCircuitException>(),
        FallbackAction = args => Outcome.FromResultAsValueTask("Платіж поставлено в чергу на обробку (Fallback)")
    })
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions<string>
    {
        FailureRatio = 0.5,
        MinimumThroughput = 3,
        BreakDuration = TimeSpan.FromSeconds(2)
    })
    .Build();
```
* **Очікувана поведінка та лог:** Запити #1–#3 доходять до шлюзу, викликають помилку і відкривають ланцюг (`[CircuitBreaker] Ланцюг РОЗІМКНЕНО`). Запит #4 миттєво перехоплюється на рівні `Fallback` без виклику `ProcessPayment`. Після паузи 2.2 с запит #5 проходить у стані `Half-Open` і закриває ланцюг (`Closed`).

### Сценарій 3: Зависання генерації аналітичного звіту (`ReportTimeoutScenario`)
* **Опис проблеми:** Зовнішній сервіс може прийняти з'єднання, але «зависнути» на кілька хвилин при формуванні важкого звіту, блокуючи ресурси клієнта.
* **Обрана політика та обґрунтування:** Комбінація **`Retry` (зовнішня стратегія) + `Timeout` (внутрішня стратегія)**.
  * `Timeout` обмежує час виконання кожної окремої спроби до 500 мс і скасовує її через `CancellationToken` (`TimeoutRejectedException`).
  * Зовнішній `Retry` перехоплює `TimeoutRejectedException` і запускає повторну спробу, яка завершується за 200 мс.
* **Фрагмент коду налаштування пайплайну:**
```csharp
var pipeline = new ResiliencePipelineBuilder<string>()
    .AddRetry(new RetryStrategyOptions<string>
    {
        ShouldHandle = new PredicateBuilder<string>().Handle<TimeoutRejectedException>(),
        MaxRetryAttempts = 2,
        Delay = TimeSpan.FromMilliseconds(200)
    })
    .AddTimeout(new TimeoutStrategyOptions
    {
        Timeout = TimeSpan.FromMilliseconds(500)
    })
    .Build();
```
* **Очікувана поведінка та лог:** Перша спроба триває 1200 мс, тому на 500-й мс спрацьовує `[Timeout]`, після чого `[Retry]` запускає другу спробу, яка вкладається у ліміт 200 мс і повертає ім'я файлу звіту.

## 2. Загальні висновки: переваги та обмеження Polly

### Переваги використання Polly
1. **Відокремлення бізнес-логіки від логіки надійності:** Розробник пише чистий код виклику сервісу, а правила повторів, таймаутів і фолбеків конфігуруються декларативно через `ResiliencePipelineBuilder`.
2. **Компонованість стратегій:** Можливість об'єднувати `Fallback` → `Retry` → `Circuit Breaker` → `Timeout` в єдиний конвеєр, де кожен рівень відповідає за свій клас збоїв.
3. **Висока продуктивність (Polly v8):** Новий API `ResiliencePipeline` оптимізований під мінімальні алокації пам'яті (`ValueTask`) і підтримує як синхронний, так і асинхронний код.

### Обмеження та ризики, які потрібно враховувати
1. **Вимога ідемпотентності:** Застосовувати `Retry` до неідемпотентних операцій (наприклад, списання коштів без унікального ключа транзакції) небезпечно, оскільки повторний запит може призвести до подвійного списання.
2. **Збільшення часу відповіді користувачеві:** Занадто велика кількість повторів або довгі затримки (`Delay`) змушують клієнта чекати замість швидкого повідомлення про помилку.
3. **Кооперативне скасування для `Timeout`:** У синхронному режимі стратегія `Timeout` покладається на `CancellationToken` — якщо код всередині ігнорує токен скасування, перервати завислий потік миттєво не вдасться.
